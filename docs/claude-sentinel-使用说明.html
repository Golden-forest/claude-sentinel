USAGE MANUAL · v0.1.0 · 2026-11-23

claude-sentinel

Claude Code 额度自愈哨兵。限额 429 阵亡之后，它自己等到重置时刻，核验无误，替你把「continue」敲回去。你唯一要做的事：什么都不做。

检测模式 事件驱动 · 零轮询
常驻开销 单进程 ≈15MB
安全策略 拿不准绝不操作
质量 40+ 测试 · 三遍审查全过
01

日常使用：零操作

没有新命令要记。你照常 cc-glm 开工，剩下的链条全自动。

自动发生的事

每次新开 Claude Code 会话，SessionStart 钩子自动把「会话 ↔ tmux 窗口 ↔ 进程」写进绑定表；额度 429 阵亡时 StopFailure 钩子立刻上报，守护进程解析重置时刻（优先读结构化 resetsAt 时间戳），睡到重置 + 裕量，然后过七道闸门核验，向绑定的那个窗口敲下 continue。会话结束自动解绑。

什么时候需要你

只有一种情况：状态退到 NEEDS_REVIEW（绑定丢失 / 发送失败 / 判断不了）。此时去对应会话里说声「继续」即可——它宁可退位也不乱敲。

02

它是怎么工作的

三段式：两个无轮询的事件入口，一个做全部决策的常驻核心，一个受控的动作出口。

architecture

FSEvents 监听   jsonl 追加的补偿通道：钩子漏的它兜（cursor 断点续读）
        │  socket 直投；守护进程离线则原子落 spool，重启导入
        ▼
sentinel watch 守护进程（launchd 常驻，单实例锁）
  分类 → 状态机（epoch 持久化）→ 定时 → Recovery Guard
        ▼
七道闸门：终态？绑定有效？进程活着且启动时间一致？pane 在？
  非 copy-mode？重置已到？没人抢先续过？——全过才放行
        ▼
tmux send-keys  文本与 Enter 分离、参数数组、绝不 shell 拼接
03

v0.1.0 实现清单

检测双通道

钩子事件（主）+ FSEvents 文件监听（兜底）。报错从屏幕轮询改为持久化数据源，一闪而过的横幅再也漏不掉。

解析重置时间三级

结构化 epoch 优先，其次带时区明文，再次中文正则（带 ±7 天合理性校验）。解析不出 → 不动作。

绑定确定性身份

SessionStart 建立会话↔pane↔pid 绑定，校验含进程启动时间（防 PID 复用）；绑定持久化，守护进程重启不丢。

安全七道闸门

发送前逐项核验；同项目开多个窗口绝不敲错；用户手动续过/原生已恢复 → 自动退位。终态事故不被重复事件复活，attempts 上限 6。

可靠崩溃安全

状态写入原子（tmp+fsync+rename）；发送前落 VERIFYING 检查点，崩溃恢复后宁可退人工不重发；spool 积压不死锁；损坏状态隔离+备份恢复。

工程实测背书

10 个 Go 包 40+ 测试全绿（含 -race 竞争检测）；端到端在真实 tmux 上验证；矩阵测试：三窗口零误发、重复事件单次发送、server_error 不误触发；独立 opus 模型整分支审查的 3 Critical + 8 Important 全部修复；真实智谱 429 载荷（error: rate_limit）实测坐实。

04

命令手册

二进制在 ~/Projects/claude-sentinel/bin/sentinel。日常只会用到第一个。

commands
# 看状态（守护进程 / 待处理事故）
~/Projects/claude-sentinel/bin/sentinel status

# 安装（钩子结构化合并 + launchd 守护；已装好，不用再跑）
~/Projects/claude-sentinel/bin/sentinel install

# 卸载（只删自己的条目，不碰其他钩子）
~/Projects/claude-sentinel/bin/sentinel uninstall

# 手动拉起守护（正常由 launchd 自动管理，排障才用）
~/Projects/claude-sentinel/bin/sentinel watch

status 输出怎么读

输出行含义你要做什么
daemon: RUNNING守护进程在岗—
daemon: DOWN守护没跑（少见）见下方故障排查
incident … SCHEDULED已捕获事故，正在等重置等它自动续，无需动作
incident … SENT_UNCONFIRMED已敲出 continue—
incident … NEEDS_REVIEW它拿不准，退位人工去对应会话说「继续」
spool: N pending守护离线期间积压 N 条事件守护恢复后自动导入
05

一次额度阵亡的完整旅程

DETECTED→ SCHEDULED→ VERIFYING→ SENT_UNCONFIRMED→ RESOLVED ✓

异常出口：NEEDS_REVIEW（拿不准，交还给你）CANCELLED（你已处理）

唯一的「人工干预点」。

看到 NEEDS_REVIEW 不用慌，它意味着「我检测到了事故，但某个核验没过」——最常见的两种：守护进程重启导致绑定丢失（会话其实活得好好的）、或发送时 tmux 不在。处理方式固定：去那个 Claude 会话里手动说一句「继续」。它永远不会因为 NEEDS_REVIEW 自己再敲键。

06

文件布局与日志

~/.local/state/claude-sentinel/
bus.sock                  # 钩子→守护的 unix socket
state.json                # 事故状态机（原子写，自动备份 .bak）
state.json.bindings.json  # 会话绑定表（重启恢复）
spool/                    # 守护离线时的事件兜底队列
logs/watch.log            # 守护进程日志（每次绑定/事故/发送都有记录）

# 看今天的动作记录：
tail -30 ~/.local/state/claude-sentinel/logs/watch.log

日志脱敏：只记错误类型、路径与事故 ID，不落完整对话内容。

07

故障排查

status 显示 DOWN

launchd 会自动拉起（KeepAlive）。若持续 DOWN：

launchctl kickstart -k gui/$(id -u)/com.hl.claude-sentinel.watch
tail -20 ~/.local/state/claude-sentinel/logs/watch.log

撞额度了却没自动续

按序查：① sentinel status 有无 incident；② 日志里有无 NEEDS_REVIEW 原因；③ 该会话是否在守护启动之前就开了（老会话无绑定，属预期安全行为，新会话起全覆盖）。

回滚到旧版（五分钟）

~/Projects/claude-sentinel/bin/sentinel uninstall
npm i -g claude-auto-retry && claude-auto-retry install

sentinel 的 uninstall 只删自己的三条钩子和 launchd，不碰任何其他配置。

08

已知边界（诚实清单）

老会话无绑定

切换前已开的会话（含当时那个正在跑的）没有绑定记录，撞限会退人工。新会话起全覆盖。

发送失败不重试

设计决策：半失败态重试可能向输入框叠字，宁可退 NEEDS_REVIEW 换安全。

v0.1.1 待办

13 条 Minor 已记录在案：日志按天轮转、NEEDS_REVIEW 桌面通知、.bak 原子性等，不阻塞使用。

设计哲学一句话。

这个工具的追求不是「永远能续跑」，而是「每一次自动操作都有据可查、可回溯，拿不准就退位给人工」。Claude Code 没有提供事务式的会话恢复 API，所以绝对承诺不存在——但每一次它敲下的键，你都查得到为什么。
